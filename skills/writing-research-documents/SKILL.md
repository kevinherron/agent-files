# Writing Research Documents

Writing a research document is a deep research task.
It requires thorough investigation across multiple sources — codebase, specifications,
external documentation, other implementations — before any writing begins.
The quality of the document is bounded by the depth of the research behind it.

Read `references/research-guide.md` before writing.
It contains guidance on what research docs are for, what questions they should answer,
structural patterns, conventions, and quality signals.
The structural patterns are starting points, not templates to fill in mechanically —
research docs vary widely in shape.
The guide's Conventions and Quality signals sections, however, apply to every research
doc.

## Before writing

Research docs require real investigation.
Before drafting:

- Read the relevant source code, specs, or external documentation
- Understand the problem space well enough to explain it to someone else
- Identify what you know, what you don’t know, and what matters

Do the research first, then write it up.
A research doc that restates the user’s question back as section headings without adding
substance is worthless.

## Conducting the research

If the user mentions specific files, documents, or tickets — read them fully in the main
context before doing anything else.
You need that context to decompose the question well.

Break the research question into sub-questions and investigate each against real sources
— code, specs, external documentation, other implementations, web resources.
Don’t try to answer the whole question at once.

**Scale the research to the request.** A targeted question or bug investigation warrants
a couple of subagents and a short doc; a spec-plus-codebase full treatment warrants
broader fan-out.
If the scope or intended depth is ambiguous, present the sub-questions you plan to
investigate and roughly how deep you intend to go, and wait for the user’s response
before fanning out.
If you’re running non-interactively, proceed and carry unresolved scope assumptions into
the document’s open questions instead of silently deciding them.

**Use parallel subagents to investigate.** Decompose the research into independent areas
and spawn an Agent for each one.
Each agent should have a focused, specific question to answer — “find where session
tokens are created and trace their lifecycle” rather than “research the auth system.”
Run agents in parallel when their questions are independent.
Keep the main context focused on decomposition, verification, and synthesis, not deep
file reading.

Every subagent prompt must spell out what to return: verbatim code snippets or spec
quotes with `file:line` for every load-bearing claim, the list of files or sections
examined, and explicit “could not determine” items.
A finding that comes back without a citation is unverified — re-investigate it or record
it as an open question; don’t inline it as fact.

**Verify before synthesizing.** Subagent findings are claims, not facts.
Re-read the cited lines for any claim the document’s conclusions will rest on.
Treat “only,” “never,” and “always” claims with suspicion — grep for the counterexample
(another call site, another config reader) before accepting them.
When a claim is cheaply testable — behavior, configuration, dead code — run the code or
a one-off test instead of inferring from reading.

Once all agents have reported back and their key claims are verified, synthesize across
their findings.
This is the step that separates a research doc from a reading log.
How does what the spec says relate to what the code actually does?
How do other implementations compare to each other and to ours?
Where do sources agree, and where do they contradict?
The connections between findings are often more valuable than the individual findings
themselves.

The research is done when every sub-question either has evidence-backed findings or is
explicitly recorded as an open question with a reason it remains open.
If verification or synthesis surfaces a new material sub-question, run one more focused
round of investigation, then stop and write.

## Choosing a structure

The guide describes several structural patterns (spec + codebase + design, codebase
survey, investigation / root cause, technology evaluation, comparative analysis).
Pick the one that fits the investigation, or combine elements from multiple patterns.
The structure should serve the content, not the other way around.

If the investigation doesn’t fit any of the suggested patterns, invent a structure that
does. The guide’s patterns are starting points, not constraints.

## Output

Write the research document as a single Markdown file.
Follow the repo’s existing convention for research docs (`docs/research/`, `research/`,
`docs/notes/`, etc.); if none exists, use `docs/research/YYYY-MM-DD-<topic-slug>.md`.
The user’s requested location wins over both.

## Generating metadata

Use `scripts/research-metadata.sh` to generate YAML frontmatter for every research
document. The script captures date, researcher, git commit, branch, repository, a
`dirty: true` flag when the tree has uncommitted changes, topic, tags, status, and
`last_updated` fields — so the document is traceable to the exact codebase state it
reflects.

The script lives in this skill’s `scripts/` directory.
You know the skill’s absolute path from the invocation context — run the script by that
absolute path (no environment variable provides it).
Pass `--repo /path/to/repo` pointing at the repository the research is *about* (or run
from that repository), not the repository the document happens to live in — otherwise
the frontmatter pins the wrong codebase.

**New document** — run the script and place its output at the top of the file:

```bash
bash <skill-dir>/scripts/research-metadata.sh \
  --repo /path/to/researched/repo \
  --topic "Description of what was researched" \
  --tags "research,relevant,tags" \
  --status "complete"
```

`--status` defaults to `complete`; use `draft` or `in-progress` when appropriate.
`--tags` defaults to `research,codebase`.

**Updating an existing document** — run in update mode and merge the output into the
existing frontmatter (replace `last_updated`, `last_updated_by`, add
`last_updated_note`):

```bash
bash <skill-dir>/scripts/research-metadata.sh \
  --update --note "Description of what changed"
```

## What to always include

Regardless of structure, every research doc needs:

- YAML frontmatter generated by `scripts/research-metadata.sh` (see above)
- A clear title and opening summary (what was investigated and why)
- References to source material (specs, docs, source files, related research)
- Connections across sources — how findings from different areas relate to each other,
  where they agree, and where they conflict
- Self-contained evidence: inline the key evidence (quote the spec passage, show the
  code snippet, include the numbers) so the reader can follow the reasoning without
  chasing down every reference.
  Link to sources for follow-up, but don’t make the reader go read them to understand
  the findings.
- Explicit open questions — what remains unknown and why it matters

## The most common failure mode

The most common failure mode in research docs is conclusions without evidence.
Don’t just state what you found — show it.
Quote the relevant spec passage, include the code snippet with file path and line
number, link to the specific documentation section, cite the GitHub issue.
Vague references ("the auth module handles this," “the spec covers this case”) aren’t
evidence. The reader needs to evaluate your reasoning, not just trust your conclusions.

The second most common failure is not distinguishing fact from interpretation.
“The spec requires X” is a fact.
“We should do Y” is a recommendation.
Keep them structurally separate so the reader can agree with the facts while questioning
the interpretation.

The third is prescribing when the doc’s job is to describe.
Some doc types exist to produce a recommendation — a technology evaluation ends in a
recommendation, a root cause analysis in a recommended fix, a comparative analysis in
“what this means for our approach.”
For those, put the recommendation in a clearly labeled final section, structurally
separate from the findings.
For neutral surveys and investigations, include recommendations only if the user asks.
When findings sections drift into “we should refactor this” or “the right approach would
be,” the document stops being a neutral record and starts being an argument — and the
reader can no longer trust it as a factual account.

## Follow-up research

When the user asks follow-up questions about an existing research document, append to
the same document rather than creating a new one:

1. Locate the existing document: check the repo’s research docs directory first
   (`docs/research/` by default); if it isn’t there, grep for frontmatter fields the
   metadata script emits (`topic:`, `git_commit:`, `researcher:`).
2. Run the metadata script in update mode to get fresh timestamps:
   ```bash
   bash <skill-dir>/scripts/research-metadata.sh \
     --update --note "Brief description of the follow-up"
   ```
3. Merge the output into the existing frontmatter — replace `last_updated` and
   `last_updated_by`, add or replace `last_updated_note`.
4. Add a new section at the end: `## Follow-up: [topic]`
5. Spawn new subagents as needed for the additional investigation.

## File references and permalinks

When citing codebase locations, use `path/to/File.ext:line` with line numbers where
precision matters. If the document is being written in a GitHub-linked repository,
convert key file references to GitHub permalinks:

```
https://github.com/{owner}/{repo}/blob/{commit}/{file}#L{line}
https://github.com/{owner}/{repo}/blob/{commit}/{file}#L{start}-L{end}
```

Use `gh repo view --json nameWithOwner -q .nameWithOwner` to get `{owner}/{repo}`.
Each permalink’s commit hash must come from the repository the cited file actually
lives in — the frontmatter hash is only valid for the frontmatter’s repository.
Only emit permalinks for commits that exist on the remote (check with
`git branch -r --contains <commit>`); a permalink to an unpushed commit is a dead link
for every reader — worse than a local path.
If `gh` is not available or the repository is not GitHub-linked, use local file paths —
they go stale but are still valuable when the research is fresh.
